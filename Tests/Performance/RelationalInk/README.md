# GUI-278: относительные биты радиуса штриха

## Результат

На Apple M5 Max выбранное относительное кодирование **не ускорило** восстановление
геометрии. Оно уменьшило полезные данные узлов примерно на 21%, но обычное
8-битное числовое кодирование оказалось немного меньше, быстрее и точнее.
Это результат одного конкретного механизма, **не опровержение общей идеи
отношений и не испытание тензорного GPU-рендерера**. Production не менялся.

### Основной случай: 79 измеренных траекторий, 11 159 узлов

Координаты взяты из существующего `QuickShapeMeasured.json`; нажим/радиус
**синтетический**. Время — медиана трёх медиан отдельных процессов. Каждый
процесс: 2 разогрева + 10 измерений, порядок вариантов циклически меняется.

| Представление | Полезные байты узлов и таблицы | Восстановление + геометрия, мс | Кодирование + восстановление + геометрия, мс | Макс. смещение вершины, pt |
|---|---:|---:|---:|---:|
| Текущий `RenderPoint` | 357 088 | 0,3919 | 0,3944 | 0 |
| Float32, отдельные массивы | 312 452 | 0,4049 | 0,4368 | 0 |
| Обычное 8-битное | 279 607 | 0,4165 | 0,4985 | 0,01216 |
| Относительное 8-битное | 281 871 | 0,4242 | 0,6252 | 0,03065 |
| Относительное 12-битное | 302 830 | 0,4267 | 0,6245 | 0,00205 |

У относительного 8-битного варианта только радиусы занимают в **3,43 раза**
меньше места, но все узлы вместе — лишь на **21,06%** меньше. Если одновременно
удерживать и узлы, и одинаковые готовые треугольники (2 309 376 байт), разница
составляет **2,82%**. Это расчёт полезных данных, не измерение RSS приложения.
Восстановление с геометрией медленнее текущего на 8,2%; полный проверенный
проход с кодированием — на 58,5%. Он не моделирует текущий инкрементальный ввод.

Длинный синтетический штрих на 100 000 узлов подтвердил направление:
3,3265 → 3,6348 мс для восстановления с геометрией; 3,2795 → 5,2836 мс с
кодированием. Память узлов 3 200 000 → 2 513 528 байт. Это один длинный штрих,
**не 100 000 предметов сцены**.

## Проверяемая гипотеза, а не подмена смысла

В прототипе выбран конкретный закон: бит на уровне `k` меняет предыдущий
восстановленный радиус в `2^(±2^-k)` раза. `0` задаёт сжатие, `1` — расширение;
на первом уровне это буквально `1/2` и `2/1`, на следующих — их корни.
Порядок битов важен: каждый разряд относится к своему масштабу. Этот закон
**добавлен нами для измеримого эксперимента**, а не выведен из формулировки Амира.

- Проверяются 4, 8 и 12 бит на узел, упакованные в байты без расширения до UInt16.
- Предыдущий восстановленный радиус — опора следующего; обратная связь в кодере
  ограничивает ошибку каждого узла вместо её бесконтрольного накопления.
- Раз в 64 узла записываются точный Float32-радиус и индекс исключений.
- Слишком большой скачок получает абсолютное исключение, а не молчаливое обрезание.
- Код 0 зарезервирован под исключение. Между якорями отдельного кода «без изменения»
  нет: постоянный радиус слегка колеблется. Это ограничение именно данного закона.
- Для быстрого декодирования используется таблица произведений операторов;
  её эквивалентность последовательному применению проверяется для всех кодов.
- Обычный контроль хранит радиус в равномерной шкале min/max каждого штриха
  с тем же числом бит. У него нет зависимости от предыдущего радиуса.
- Дополнительный Float32-контроль отделяет эффект структуры массивов/выравнивания
  от эффекта потери точности. Он экономит 12,5% без изменения геометрии.

Это **слой кодирования локального размера**, не готовая тензорная память.
Поворот, анизотропия, глубина внутреннего разбиения узла и вычисление геометрии
непосредственно из битов на GPU здесь не реализованы. Для честного первого
сравнения все варианты вызывают **тот же неизменённый** `InkStrokeGeometry`.
Дублирующего построителя треугольников нет.

## Связь с реальным Notebook

`SpatialInkGeometry.renderPoint` превращает измеренную ширину в радиус;
`InkStrokeGeometry.appendStrokeVertices` строит треугольники для действующего
Metal-пути. Этот исходник компилируется прямо в стенд, без его копии.
Позиции и цвет каждого узла сохранены побитно, топология треугольников одинакова.

Но `SpatialInkCanvas.makePoint` сейчас сохраняет **постоянную ширину пера**:
нажим влияет на прозрачность. Переменная толщина — предложенное новое поведение,
а не ускорение того же текущего пользовательского сценария. Для постоянной
ширины достаточно одного значения на штрих; битовый кодер радиуса ему не нужен.

## Достаточный сигнал и границы

Шесть корпусов: постоянный, плавный, скачкообразный и шумный радиус;
измеренные траектории с синтетическим радиусом; один длинный штрих.
Каждый процесс прошёл 1 691 176 проверок packing/restart/escape, границ ошибки,
неизменности координат/цвета и совпадения числа вершин. Это количество
утверждений, а не независимых тестовых сценариев.

Предварительный критерий — смещение соответствующих вершин не больше 0,1 pt
документа. Относительные 8/12 бит прошли на всех корпусах. Относительные 4 бита
не прошли: максимум 0,5601 pt. Контур при 8 битах визуально осмотрен на
`Results/contours.png`; это не равенство изображения при произвольном zoom.

Измерялись тёплые CPU-проходы, включая выделение массивов результата, но без
последующего потребления результата и его освобождения. Все вершины читаются
после остановки часов, чтобы результат не мог свестись к фиктивному count-only
тесту. Полная подготовка штриха не заменяет проверку `IncrementalInkMesh`.

Память — занятый payload массивов + одна таблица соответствующего варианта.
Не включены capacity, заголовки объектов, исходные force/time/azimuth/altitude,
SQL/архив, пространственный индекс, растровые кэши и GPU-буферы. Одновременно
удерживаемые стендом входные данные не выдаются за потребление будущего приложения.
FPS, CPU/GPU utilisation, энергопотребление, задержка Pencil и физический iPad
**не измерялись**. Установленные приложения и пользовательское содержание не тронуты.

## Повторить

Из корня checkout:

```sh
Tests/Performance/RelationalInk/run.sh
```

Нужны macOS и Xcode Command Line Tools. Скрипт компилирует Swift с
`-O -whole-module-optimization`, создаёт `.build/relational-ink/`, записывает
хеши исходников/фикстуры, сведения об окружении, JSON сырых измерений и PNG.
Он не собирает и не устанавливает приложения, не запускает MCP и не читает архивы.

`Results/runs.json` содержит три фактически выполненных процесса с полными
выборками времени. `Results/environment.txt` фиксирует окружение и исходники.

**Решение:** не внедрять этот кодер как ускорение Notebook. Сжатие данных
достижимо, но для него обычное числовое представление здесь выгоднее. Проверка
другого закона отношений или прямого GPU-пути будет отдельным экспериментом.
