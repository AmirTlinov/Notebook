# GUI-280: локальная перерисовка тензорных чернил

**Результат:** на синтетической сцене из миллиона узлов адресная правка 32 узлов
с обновлением изображения занимает на GPU примерно в **15 раз меньше времени**,
полный цикл с CPU и ожиданием GPU — в **2,5–4,0 раза меньше**. Это выигрыш от
исключения неизменившейся работы, не от нового смысла битов или тензорных операций.
На небольших сценах полного ускорения нет. Приложения не изменены.

## Один геометрический путь

Использован прямой `bitShapeGPU` из GUI-279: одно 32-битное слово формы узла,
изменение общего размера ×2 / ×1/2 на GPU, тот же `evaluate` в Metal и тот же
source-over fragment shader. Общая подготовка/отрисовка вынесена из
`TensorGPU/main.swift` в `TensorGPU/Support.swift`, без второй реализации.

После первого полного кадра сохраняется изображение 1536×1024. Производный
индекс связывает адрес узла с участками по 64 сегмента и плитками 128×128:

1. Правка затрагивает только известные узлы и содержащие их участки. CPU меняет
   консервативные границы; авторитетное слово формы остаётся только на GPU.
2. Повреждёнными считаются **старые и новые** плитки изменившихся участков.
3. Каждая такая плитка очищается и рисуется заново всеми пересекающими её
   участками **в исходном порядке**, включая неизменившиеся полупрозрачные штрихи.
4. Плитка с 4×MSAA разрешается и копируется в сохранённое изображение. Всё это,
   вместе с правкой формы, — один command buffer, без ожиданий между плитками.

У индекса есть число индексов геометрии на плитку. Если сумма работы повреждённых
плиток не меньше полного кадра, **сразу выбирается полный проход**: до обхода и
сортировки всех его участников. Это выбор области одного рендерера, не legacy
fallback. Простой критерий не моделирует стоимость draw calls и не обещает
оптимальный выбор на маленьких сценах.

Индекс находится только в эксперименте, рядом с production-владельцем
пространственного поиска не устанавливается. Здесь нет поиска узла по содержимому
и обхода всей сцены на правку, но есть адресное чтение памяти, отбор участников
плиток, сортировка порядка и собственно растеризация.

## Измерения: Apple M5 Max

Шесть независимых процессов, последовательно; в каждом 4 разогрева
+ 30 измерений на сценарий. Полная и локальная отрисовки чередуются по порядку;
имеют отдельные одинаковые буферы формы. Все узлы лежат внутри viewport.
Таблица — медиана шести медиан, миллисекунды:

| Сцена | GPU, полный → локальный | Полный цикл, полный → локальный |
|---|---:|---:|
| 10 000 узлов | 0,1737 → 0,1387 | 0,3158 → 0,3249 |
| 100 000 узлов | 0,2054 → 0,0850 | 0,3456 → 0,2711 |
| 1 000 000 узлов | 0,6480 → 0,0423 | 0,7872 → 0,2726 |
| 100 000, плотное наложение; выбран полный кадр | 0,1398 → 0,1403 | 0,2786 → 0,2875 |

Для первых трёх сцен локальная плотность одинакова: восемь штрихов, 2000 узлов.
Дополнительные штрихи лежат в другой части **того же видимого кадра**, а не за
его пределами. Изменяются 32 узла, обновляются 4 из 96 плиток: 65 536 пикселей,
4,17% изображения. Передаются **18 738 индексов** в 23 draw calls, вместо
6 264 000 индексов на миллионе узлов — в 334 раза меньше. Это не число вызовов
vertex shader и не ускорение в 334 раза. 2000 — число уникальных исходных узлов
переигрываемых участков, не счётчик физических чтений памяти GPU.

Отношения времён полного/локального прохода **внутри каждого процесса**:

| Сцена | GPU: шесть отношений | Полный цикл: шесть отношений |
|---|---|---|
| 10 000 | 1,280 / 1,273 / 1,290 / 1,258 / 1,246 / 1,235 | 0,975 / 0,973 / 0,920 / 0,971 / 0,929 / 1,003 |
| 100 000 | 2,384 / 2,433 / 2,339 / 3,419 / 2,413 / 2,335 | 1,305 / 1,475 / 0,932 / 1,307 / 1,365 / 1,177 |
| 1 000 000 | 14,862 / 15,024 / 15,052 / 15,777 / 17,032 / 13,020 | 2,528 / 2,677 / 2,673 / 3,206 / 4,015 / 3,190 |
| Плотное наложение | 0,995 / 0,922 / 0,985 / 1,008 / 0,983 / 0,996 | 0,973 / 0,969 / 0,998 / 0,939 / 0,989 / 0,981 |

Абсолютные времена между процессами меняются. На 100 тысячах один процесс даже
дал небольшое замедление полного цикла; стабильного end-to-end выигрыша для этой
нагрузки не заявляем. На миллионе он воспроизвёлся во всех шести процессах.
CPU-подготовка/отправка на миллионе выросла с 0,0153 до 0,0556 мс: списки,
23 draw calls и копирования не бесплатны. Поэтому 15× GPU превращаются примерно
в 2,9× полного цикла. GPU timing включает compute, render и tile blits;
полный цикл — также CPU-планирование/отправку и ожидание GPU. Чтение пикселей для
сравнения и PNG не входит в замеры. Это offscreen latency, **не FPS экрана**.

В плотном контроле плиточный план потребовал бы 936 900 индексов против 626 400
полного кадра. Ранний выбор полного прохода устраняет эту лишнюю работу, но
оставляет расходы поддержки границ. Локальная правка среди множества перекрытий
не становится дешёвой только потому, что изменены 32 узла.

## Цена памяти и первого кадра

| Узлы | Полезные данные CPU-индекса, байт | Построение индекса, диапазон мс |
|---|---:|---:|
| 10 000 | 140 608 | 0,263–0,280 |
| 100 000 | 1 401 024 | 2,497–2,602 |
| 1 000 000 | 14 005 824 | 25,433–30,961 |

Это используемые элементы массивов/множеств, **без запасной ёмкости и заголовков
аллокатора, не RSS**. Построение O(N), подготовка GPU и первый полный кадр платятся
до локальных замеров. Холодное открытие этим опытом не ускорено.

GPU-геометрия на миллионе: 61 120 000 байт на состояние. Сохранённое изображение:
6 291 456 байт; плиточные MSAA+resolve: 327 680 байт расчётного пиксельного
хранилища. Для адаптивного полного прохода общий рендерер **сохраняет** полноразмерный
MSAA target (25 165 824 байт); его устранение и экономия общей памяти не заявляются.
Стенд держит также независимое контрольное состояние и изображение.

## Качество и границы

Каждый из шести процессов: **624 проверки PASS**. На всех проверенных кадрах
RGBA локального и полного результатов совпали побитно. Отдельный пример с
пересечениями полупрозрачных штрихов увеличивается трижды ×2, пересекает границы
плиток, затем трижды уменьшается ×1/2:

- все шесть шагов действительно используют плиточный путь;
- незатронутые плитки побитно неизменны;
- сжатие удаляет прежний контур, итог точно совпадает с начальным;
- перестановка порядка штрихов даёт 238 отличающихся пикселей;
- намеренно неполная очистка старой области даёт 287 отличающихся пикселей.

Настоящие Metal PNG сохранены и осмотрены. Общая геометрия после выделения
`Support.swift` повторно проверена прежним стендом: **3892 проверки PASS**;
квитанция сохранена отдельно, старые исторические таблицы GUI-279 не переписаны.

Это изолированный опыт для **неподвижной камеры/viewport и неизменной связности**,
известных адресов и общего масштаба формы в ненасыщающемся диапазоне. Произвольное
перемещение, поворот/анизотропия границ, добавление точек, ластик, группы,
LOD и инкрементальный Pencil-путь не интегрированы. Тензорные операции GUI-279
не означают, что этот индекс уже поддерживает каждую из них. Физический iPad,
экранные кадры, энергия и 30-минутная совместная сессия не проверялись.

## Повторение

Из корня checkout на Mac с Metal toolchain:

```sh
Tests/Performance/TensorTiles/run.sh
Tests/Performance/TensorGPU/run.sh .build/tensor-tiles/direct-regression
```

Повторный процесс без пересборки:

```sh
mkdir -p .build/tensor-tiles/run2
.build/tensor-tiles/probe .build/tensor-tiles/ink.metallib unused .build/tensor-tiles/run2
```

`Results/run{1,2,3,4,5,6}.json` содержит все отдельные времена, p95, планы и сравнения.
`environment.txt` фиксирует исходники/компиляторы/машину; первая строка — HEAD до
фиксации изменения, а SHA-256 соответствуют реально проверенным исходникам.
`binary-hashes.txt` связывает процессы 4–6 с одним бинарником. Процессы 1–3
относятся к `*-precleanup.txt`: единственная разница исходников — удалённая
пустая строка в конце `Support.swift`. Они сохранены, а не отброшены в пользу
более быстрых новых замеров. PNG относятся к процессу 4; `direct-regression*` —
отдельная проверка общего рендерера на окончательных исходниках.
