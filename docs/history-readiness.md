# History readiness

GUI-535 compares this Mac and Elizabeth's iPad through their installed native
owners before the birth/event transition. The accepted installed baseline is
DB29, wire44 and manifest26. DB30 adds the local disposable page-material index;
authored content, history, wire44 and manifest26 stay unchanged.

## Owners

- `NotebookHistoryReadiness` owns the workspace admission phase and one request.
  `NotebookWorkspaceHistory` connects it to the existing input, program, account
  and delivery owners; Launch supplies its actual catalog-operation lifetime.
- `NotebookPersistenceQueue` drains accepted work and retains failed/uncertain
  writes for the same Retry. Its actual writer seal closes the final SQL boundary.
- `NearbySync` joins the selected TLS session's callbacks and advertised prefixes.
  Its bounded control lane carries UUIDs, hashes and counts through existing credit.
- `NotebookCommandReader` borrows its existing connection. `NotebookQueryCut`,
  replica inventory and physical closure authenticate finite source observations.
  `NotebookHistoryStreamAccumulator` binds the six streams to the exact pair/cut.

## Request

The installed direct MCP exposes `notebook_history_readiness` with `operation`
(`start`, `status`, `cancel`) and caller-stable `requestID`. Start also names exactly
two distinct `deviceIDs`. Status/cancel use that same ID. Core-only IPC reports
`native_owner_required`; the native owner performs the comparison.

Start checks directory, saved trust, actual account, installed build, journal
generations and selected connection. Extra/offline/blocked recipients remain
explicit inventory and can refuse the declared pair. Readiness never retires them.

Start requires the actual catalog owner to be idle; an accepted catalog operation
finishes through that owner before a new readiness attempt. The phase then closes
new authorship, joins accepted input/checkpoint/account/cloud work, and drains both
advertised delivery prefixes. After writer seals,
each source sends `acceptedTransactions`, `physicalClosures`, `sourceOriginalRoots`,
`replicaInventory`, `replicaControl` and `fleet`; both owners confirm all twelve
roots. Changed lifetime, control observation, prefix, account or connection
invalidates that request. Cleanup releases the same seals and resumes the same
owners before admitting new work.

After quiescence, terminal `resume` retains the first typed refusal's actual
source, stage and bounded section/transaction metadata. A remote refusal is not
echoed. Already-sent pages drain through the same TLS credit owner before the peer
terminal boundary; source reads stop cooperatively. A successful report becomes
visible only after both owners finish the resume handshake.

## Meaning of the report

`acceptedAndPhysicalMetadataMatched` describes the sealed comparison.
`readyForNextSlice` additionally requires both sources' blocker counts to be zero.
Missing original birth facts, unsupported dependencies and incomplete raw closures
remain named blockers. Raw manifest/blob hashes are checked for every declared
record, including transactions with zero receipts. Unknown raw fields stay stored;
large causal counters are validated from exact numeric tokens before typed decode.

Counts/cursors cross native JSON as decimal strings. Read queries
`replicaInventory` and `historyPhysicalClosure` expose bounded metadata from their
own borrowed cut. The report keeps `formatTransitionAuthorized: false`; GUI-537
owns the guarded format activation. Exact executed scope and installed/live
results belong in [verification](verification.md), and current tasks in Linear.
