## 1. Дорогой снимок стоит между намерением и первым изменённым кадром

**Измерено на физическом iPad; сам последовательный путь также подтверждён кодом.**

Путь A: `IPadPageTurnController` → готовность соседнего host → `begin` →
main.async → `UIGraphicsImageRenderer.image` / `drawHierarchy(afterScreenUpdates: true)`
→ первый плоский curl → OS receipt → первый изгиб.

`Applications/iPad/IPadSheetCurlController.swift:99–140,160–206,209–226`:
перенос capture из обработчика касания в `DispatchQueue.main.async` **не переносит
его с главного потока** и не делает снимок готовым заранее. Пока синхронный
захват выполняется, следующий UI/input event не может исполняться на MainActor.
Capture корректно требует свежие слои: простое удаление `afterScreenUpdates`
вернуло бы риск старого штриха/пустого нового слоя, а не устранило причину.

Повторный расчёт из сохранённых 20 наблюдений, медианы в мс:

| Участок | Штатный baseline | Metal candidate02 |
| --- | ---: | ---: |
| Выполнение команды до возврата | 0.079 | 0.234 |
| Команда → начало capture | 0.129 | 0.505 |
| Capture | 28.770 | 64.790 |
| Конец capture → первое кодирование кадра | 6.520 | 22.219 |
| Конец capture → первый показанный curl-кадр | 33.600 | 40.072 |

| Команда → первый изменённый кадр | 86.038 | 106.422 |
| Команда → завершение | 384.816 | 418.920 |

Медианы участков не складываются в медиану всей цепочки. Интервал 25.010 мс
включает дальнейшее кодирование/показ, это не чистая стоимость доставки callback.
Однако зависимость от показа плоского кадра реальна: до `motion.presentation`
`render` принудительно отправляет плоский лист, а `advanceAnimation` не движется.
Этот барьер введён против мерцания; удалять его без полного корректного первого
изображения нельзя. Даже один capture 28.770 мс уже превышает весь бюджет 16.67 мс.

B убирает плоский primer, но последовательно снимает оба host и загружает две
текстуры (`IPadSheetCurlController.swift:154–235`,
`Applications/Shared/SheetCurlRenderer.swift:229–266`). У candidate02 CPU upload
занимал ещё 8.964 мс по медиане. Поэтому быстрый шейдер не дал быстрого ответа:
CPU encode кадра 2.890 → 0.082 мс, GPU curl 3.083 → 1.674 мс, но первый ответ хуже.
Это не основание возвращать качество к меньшему разрешению; надо сокращать
получение/перенос точных пикселей на критическом пути, а не только формулу изгиба.

Отдельный отвергнутый shared-buffer опыт: 96.58% capture времени пришлись на
`drawHierarchy` вместе с flush; выделение буферов не было главным расходом.
Конкретный внутренний алгоритм UIKit/цветоконверсия этим замером не доказаны.

## 2. Штатное завершение управляется часами анимации, а не скоростью руки

**Подтверждено кодом A, не новым замером.**

`IPadSheetCurlController.swift:235–275,297–313,316–327`:
`max(0.1, 0.32 * distance)` задаёт минимум 100 мс и до 320 мс на завершение.
Скорость жеста используется для решения принять/отменить, но не передаётся в
длительность. `accelerateSettlement` один раз ускоряет вдвое, не следует
дальнейшему темпу. Новый обычный pan отвергается при `motion != nil`.

Контроллер страниц сохраняет следующий контакт отдельным cold-путём
(`IPadPageTurnController.swift:247–290,693–699`), но начать его движение может
только после `!isTransitioning`. Это уже не бесконечная очередь всех анимаций:
шаги сворачиваются в `stepTarget`. Однако предыдущий лист остаётся обязательным
барьером. Именно здесь ощущение «я жду лист», даже если GPU успевает.

Ещё один лишний барьер: отмена gesture до получения image всё равно идёт в
`animate(to: 0)`. Для отмены требуется будущая readiness, capture и OS receipt;
`isTransitioning` и запрет ввода сохраняются. Если готовность не приходит,
отменённый жест сам не освобождает страницу. В B есть ранний `finish(false)`
для этого случая, но его нынешний tree после возврата UIKit-пути не проверен
на устройстве. Отмена ещё не показанного изгиба не должна создавать снимок.

## 3. Четыре host не означают ограничение памяти четырьмя дешёвыми объектами

**Факт отказа — из диагностического Simulator run115 другого чата; не физический
замер. Причина учёта и владения подтверждена кодом.**

В `arrow.log` capture требовал 65,116,800 байт, при уже занятых
199,450,624 reserved + 22,579,328 resident. Сумма 287,146,752 больше неизменного
лимита 268,435,456 на 18,711,296 байт. Команда дошла до владельца навигации,
но allocator отказал снимку — это не потерянный tap и не медленная анимация.

До нового WIP соседние `InkCanvasView` удерживали drawable pools, но не
предлагали их существующему механизму reclamation. Каждый живой host несёт
изображения, backing, геометрию и иногда WebKit, а не только UIViewController.
В A уже добавляются освобождение ненужного backing и ожидание фактического
GPU release для **того же** Motion; это работа архитектурного чата, не наш fix.

У B давление выше: `capturePair` резервирует две CPU-картинки, две sampled
texture и два drawable до capture. На старом одинаковом fixture reservation
61.945 → 123.889 MiB. Резерв держится весь переход; `Motion.image` и `sourceCover`
удерживают полноразмерный front CGImage для идентичности callback, хотя кадры
уже используют textures. Это дополнительная точка сокращения памяти после
upload, не доказанный способ уложить первый ответ в бюджет.

## 4. Новый reclaimer не защищает вторую страницу уже видимой пары

**Условный дефект проверяемого WIP A, выведенный из исполняемого пути;
физическое воспроизведение ещё отсутствует. Передан владельцу для проверки.**

Последовательность:
1. A→B уже завершается; `displayedIndex` ещё A, frozen sheet и live-подложка B нужны.
2. Новый горизонтальный контакт просит C. `prepareDirection` вызывает
   `prepareExternalTarget(C)` (`IPadPageTurnController.swift:247–262`).
3. `PageInkProjection.swift:47–55` защищает только current/demanded/installed.
   B ещё не current и не installed, demand уже C. Его `required` становится false.
4. `InkCanvasView.swift:637–675` теперь вправе отдать backing B при следующей
   аллокации. `reclaimPageBacking` скрывает Metal-слой и снимает готовность.
5. Окно host удерживает `turningIndex` B, **но это не удержание его пикселей**.
   Штатный curl использует B как живую подложку и завершает переход без
   повторной проверки её готовности.

Возможный эффект: исчезнувшая рукопись под изгибом/неподготовленная посадка.
Нельзя просто совместить такой reclaimer с ожиданием landing-ready из B:
если B уже parked и ни одна роль его не требует, получится ожидание собственной
готовности без источника продвижения. Защищать нужно обе стороны активной пары
независимо от нового намерения, сохранив тот же bounded ресурсный владелец.

## 5. Готовность проверяется не на всех границах передачи

**Дыры по коду A; их частота и вклад в наблюдаемое мерцание не измерены.**

- Захват проверяет Bool до/после (`IPadSheetCurlController.swift:124–140`),
  но не поколение содержимого. При reentrant UIKit flush переход ready→false→true
  неотличим от неизменного ready. `setPage` сообщает curl только true
  (`IPadPageTurnController.swift:677–690`), а после установки image изменение
  готовности curl вообще игнорирует. Это недостаточное доказательство свежести
  captured image, не доказательство того, что каждый снимок устарел.
- `finishPresentedEndpoint:230–233` проверяет только endpoint снимка.
  `finish:278–287` раскрывает живой host и затем разрешается ввод, не сверяясь
  с его текущей готовностью. Обновление содержимого/проекции во время изгиба
  может сделать этот host неготовым после первоначального admission.
- У ошибки capture нет проверки `motion.id == id` перед `onFailure/finish`
  (`142–156`), хотя в успешной ветке такая проверка есть. Если UIKit flush
  синхронно сменил Motion, ошибка старого снимка может завершить новый.

B содержит generation/cancellation fences и ожидание живого endpoint; это не
делает B принятым решением: полная повторная проверка этих последних правок
не выполнена, а задержка capture остаётся.

## 6. Есть повторная работа вне самого шейдера

**Подтверждённые пути, но пока без отдельной оценки их миллисекунд.**

- A `SheetCurlRenderer.swift:334–348,351–387`: CI-граф, clear pass и render
  собираются для каждого изменившегося кадра. При page curl каждый кадр также
  вызывает `waitUntilScheduled` на MainActor, даже если live-underlay не менялся.
  Нельзя просто убрать transaction fence: он держит слои согласованными.
- `IPadPageTurnController.swift:414–418,634–674,803–829`: при каждом update вне
  перехода всем сохранённым host заново назначается rootView и создаётся новый
  `PageTurnReadiness`. После landing это делается перед onCommit, а публикация
  модели снова запускает update. Это не пересоздание самих UIViewController,
  но лишняя переоценка до четырёх деревьев/обработчиков readiness.
- `NotebookAppModel.swift:136–170`: cold-read проверяет адресованную страницу,
  затем ещё глобальный `collaborationReadEpoch`. Публикация другого листа,
  документа или shared-context меняет epoch и повторяет цикл writer fence →
  reader → validation, хотя target мог не измениться. `NotebookDiskRefresh.swift:15–38`
  уже переиспользует неизменное тело; утверждать повторное полное декодирование
  было бы неверно. Остались повторные SQL/history/validation и ожидание очередей.
  Просто удалить epoch нельзя: он также защищает недолговечные локальные записи.
- `requestExternalSelection:725–734` может повторно добавлять одинаковые idle
  callbacks через `NotebookInputGate.swift:240–244` при readiness других страниц.
  Проверки target/transition предотвращают двойной переход, но не создание и
  последующее исполнение лишних замыканий. Это вторичный расход, не причина 86 мс.
- Для cold-программы пассивный WebKit готовит raster, а после выбора листа
  живой runtime запускается отдельно (`PreparedAgentElementView.swift:100–118,377–452`,
  `PageRasterPreparation.swift:80–120`). Подготовленная картинка не равна готовому
  интерактивному контролу. Поэтому тест только статических Text/Rectangle не
  доказывает немедленную работу программы после landing. Это ограничение
  текущего жизненного цикла; не повод запускать все программы тетради заранее.

## 7. В измерениях есть слепые зоны

- A `NotebookPageMotionUXTests.swift:637–661` собирает `onFramePresented`,
  а renderer вызывает его только при положительном `presentedTime`.
  Проверка «все receipts положительные» не видит отфильтрованные невалидные.
  В raw collector через `onFrameReady` baseline имел 10, candidate02 — 15
  неположительных receipts. В B строгая проверка уже оборачивает правильный
  callback, сохраняя основной handler; это не изменение порога.
- `FrameTiming.submitted` снимается **перед** commit/wait/present
  (`SheetCurlRenderer.swift:351,385–397`). Метрика CPU encode не измеряет всё
  время main-thread submission, особенно `waitUntilScheduled`.
- GPU command times измеряют curl, не внутренний render/readback UIKit,
  не весь compositor. Источник дополнительных пропусков OS-показа остаётся
  открытым до системного trace. Callback display-link не является FPS.
- 20-turn fixture вручную сообщает ready(true), поэтому не содержит настоящий
  cold decode, плотную рукопись, SVG, программы, Pencil sensing и 30-минутную работу.

## Порядок исправления по причинности

1. Не допустить потери backing обеих страниц активной пары при новом намерении;
   затем проверить отмену до capture и точную границу snapshot→live.
2. Снять контроль штатного capture на актуальной общей базе с разделением
   main-thread capture, upload, schedule/wait, OS-показа и первого следующего ввода.
3. Убрать дорогую повторную сборку/перенос полной страницы с критического пути,
   сохранив свежесть, разрешение и единый путь состава листа. «Ещё быстрее shader»
   не решает измеренную нижнюю границу ответа.
4. После этого принять непрерывное движение/перехват вместо обязательного
   завершения по часам; отдельно проверить reversal после пропуска страниц.
   B при frozen 1→5 и новом reverse-намерении 4 сначала выбирает endpoint 1
   (`endInteractiveTurn:404`), затем запускает 1→4 вперёд. Итоговый индекс может
   быть верен при неожиданной смене визуального направления; нужен сценарий,
   а не только assert конечной страницы.

Не обнаружены основания добавлять второй display clock, бесконечный page cache,
меньшее разрешение, таймер «готовности» или слабые пороги. Уже существуют
стабильные host, конечное окно, остановка curl-clock в покое, reuse CIContext
и проверки идентичности поздних callback. Эти рабочие границы сохраняются.
