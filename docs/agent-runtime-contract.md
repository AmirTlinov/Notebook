# Исполнитель вопроса в Notebook

> Этот документ описывает нынешний отдельный исполнитель, не продолжение живых
> задач Codex desktop. Нативный адаптер уже прошёл живой разговор, остановку и
> разрешение, но ещё не подключён к приложениям:
> [проверенный канал и незавершённые условия](codex-desktop-bridge.md).

## Владелец результата

`NotebookAgentExecutor` на Mac исполняет один уже принятый запрос Notebook. Он получает UUID запроса, неизменяемый вопрос, выбранное содержание и точный каталог разрешённых функций. Он не читает каталог тетрадей, не открывает хранилище и не выбирает новый объект по текущему экрану. Типизированный обработчик Notebook проверяет разрешение и передаёт изменение прежней очереди записи. Карточка на iPad, состояние запроса, сохранённый ответ и квитанции изменений принадлежат Notebook, а не истории Codex.

Один запрос создаёт один временный поток App Server; после завершения и освобождения принятых вызовов его процесс закрывается. Завершённые потоки не накапливаются в памяти фонового помощника. После сбоя приложение сохраняет прерванное состояние и уже записанные квитанции. Переподключение устройства и перезапуск Mac не запускают такой запрос повторно.

## Почему закреплены версия и модель

Поддержанный профиль — `codex-cli 0.153.4`, arm64 macOS, модель `gpt-5.5`. SHA-256 проверенного исполняемого файла: `b973d440acac501fd2594a43e7ca9ce41e0a65b9dfb28d0d7a7837c99e1261e3`. Единственный конфигурационный ресурс — `Applications/Mac/AgentRuntime/notebook.config.toml`; его отпечаток проверяет `NotebookAgentRuntimeProfile`. Модель относится только к отдельному помощнику Notebook и не меняет модель разговора человека в Codex.

Это граница проверенной возможности, а не предположение, что `dynamicTools` отключает встроенные средства. Реальный запрос к локальному проверочному провайдеру с GPT-5.5 содержит ровно namespace `notebook` и переданные ему функции. Для вопроса это `read` и `render`, для явно разрешённого изменения добавляется `apply`. Отрицательная проверка с GPT-5.6 Sol при тех же запретах всё равно получает `functions.exec` и `functions.wait`: его встроенная модель требует code mode. Такой профиль нельзя объявить совместимым. Другая версия, бинарник или конфигурация дают `unavailable`; автоматической замены модели, ослабления sandbox и перехода к обычному Codex-профилю нет.

Исполнитель извлекает исходные метаданные GPT-5.5 из встроенного каталога проверенного бинарника (`debug models --bundled`), не меняет их и передаёт этот единственный экземпляр через `model_catalog_json`. Обновление удалённого каталога не меняет форму инструментов уже принятого профиля. App Server принимает конфигурацию с `--strict-config`; после запуска проверяется эффективная конфигурация. Пустые `environments`, `runtimeWorkspaceRoots` и `selectedCapabilityRoots` вместе с явными запретами исключают доступ к рабочим файлам, оболочке, браузеру, сети через инструменты, навыкам, приложениям, чужим MCP и другим агентам. Сам сетевой запрос к модели остаётся необходимым транспортом ответа, но не инструментом произвольного доступа. [Конфигурация Codex](https://learn.chatgpt.com/docs/config-file/config-reference).

## Вход и закрытый процесс

Приложение передаёт исполнителю собственный каталог runtime — `~/Library/Application Support/Notebook Agent`, вне архива тетрадей. Авторизация не попадает в репликацию, экспорт или IPC чтения Notebook. Каталог, его рабочая папка и временные файлы находятся под правами пользователя; конечный каталог требует `0700`, конфигурация — `0600`, символьная ссылка вместо этого владельца не допускается. Пути бинарника, каталога и ресурса задаёт приложение, а не вопрос, содержимое объекта или аргументы инструмента.

Процесс получает отдельный `CODEX_HOME` и минимальное окружение. `~/.codex/config.toml`, пользовательские плагины, переменные API-ключей и существующие файлы авторизации не импортируются. `account/read` используется только для проверки управляемого входа типа `chatgpt`. Явное действие входа вызывает `account/login/start` и отдаёт приложению HTTPS-адрес OpenAI; файл с токенами читает и обновляет сам Codex. API-ключ, внешние токены и другая учётная запись не являются запасным способом выполнения. Успешный `account/login/completed` должен назвать ID начатого входа. Один ограниченный handshake сохраняет его даже при доставке в том же stdio-сообщении до возобновления ожидающего `login/start`; чужой и повторный ответ не меняет доступность. Через 300 секунд незавершённый вход отменяется. Ответы входа и stderr не попадают в карточку или журнал приложения. Управляемый вход и двусторонний stdio описаны в [документации App Server](https://learn.chatgpt.com/docs/app-server).

## Ход и ограничение разрешения

Вызов `run(requestID:prompt:context:tools:onEvent:callTool:)` принимает не более 16 функций одного пространства `notebook`. Контекст попадает в `additionalContext` с видом `untrusted`; исходный текст объекта не становится инструкцией разработчика. У приложения нет интерфейса отправки произвольного RPC, пути, команды shell или адреса провайдера из пользовательского запроса.

`NotebookAgentToolCall.id` сохраняет исходный `callId` App Server. Обработчик Notebook связывает запись и ответ с парой `requestID + callId`, поэтому потерянный ответ не разрешает второй ход. Исполнитель проверяет имя функции, пространство, ID потока и поколения хода до передачи обработчику. Неизвестный запрос сервера, повторный `callId` в том же процессе и чужой инструмент закрывают ход. Уже начатые вызовы завершаются в прежней очереди записи; поздняя отмена не превращает сохранённое действие в несостоявшееся.

Встроенные события выполнения команды, изменения файла, web search, генерации изображения, чужого MCP и subagent считаются нарушением профиля, а не новой доступной возможностью. Допуск каталога доказывается реальным запросом провайдера; обработчик событий — дополнительная защита, не замена этого доказательства.

## Источник зрения

`NotebookAgentToolResult(value:images:)` передаёт типизированные изображения отдельно от JSON-текста. `read({})` раскрывает только метаданные запроса; `read({referenceID})` — один закреплённый исходник без PNG. `render({referenceID})` получает `AgentPinnedSource.image` из того же сохранённого запроса и проверяет принадлежность действующему разрешению. Изменение выбранного объекта, камеры или текущего источника не меняет эти пиксели. Если изображение не удалось сохранить при указании, инструмент возвращает честную недоступность этого фрагмента; текущий рендер не является запасным источником.

`NotebookAgentImage` допускает только PNG: SHA-256, сигнатура, ImageIO MIME, полный успешный разбор и точные размеры проверяются до передачи. Размеры ограничены до декодирования; повреждённый файл или несовпадающий отпечаток не превращается в доказательство. App Server получает `inputImage`, а фактический запрос провайдера содержит `input_image` с теми же PNG-байтами. Это не base64 внутри текстового JSON, не путь к файлу и не удалённый URL. Метаданные рядом с изображением называют закреплённую область и ревизию; изображение не удостоверяет показ нового результата на iPad.

## Вопрос в приложении

`NotebookAgentCoordinator` начинает работу только после готовности модели и использует прежний `NotebookPersistenceQueue`. Он читает не более 16 незавершённых заголовков, проверяет доступность исполнителя и один раз атомарно занимает запрос. Все изменения, текстовые порции и завершение проходят ту же очередь, что уже принятые нативные действия. Второго писателя, сервера или чата нет. Закреплённый вопрос и разрешение нельзя заменить аргументами инструмента.

Восстановление после сбоя переводит своё прежнее `running` в `failed`, сохраняет части ответа и квитанции, но не повторяет ход. Чужое активное исполнение не присваивается вторым Mac. Запрос без доступного входа остаётся в очереди, не расходуя единственное право исполнения. Сохранённая остановка до начала даёт `stopped` без запроса к модели.

Текст накапливается одним владельцем до подтверждения SQL-записи: порция до 8 КиБ либо короткое объединение до 250 мс. Следующая порция не удаляет предыдущую при ошибке. Завершение ждёт уже принятую порцию и сохраняет остаток; ошибка записи оставляет терминальное состояние ожидающим сохранения, а не начинает модель заново. Повторное уведомление записи и повторный выход не создают второго ответа.

Проверка `input_active` возвращается немедленно из Core. Координатор повторяет тот же `callID` вне очереди не дольше четырёх секунд, с проверкой остановки перед каждым допуском; Pencil и освобождение контакта не ждут спящего писателя. Остановка закрывает допуск новых действий, ждёт действительный ACK исполнения и ранее принятые операции, затем записывает `stopped`. Для запроса изменения `completed` требует сохранённую квитанцию: текст «готово» без неё становится `failed`, а уже сохранённый текст остаётся доступен в карточке.

## Завершение, отмена и пределы

| Ресурс | Контракт |
|---|---|
| Активные запросы | Один; следующий получает `busy`, скрытой очереди нет. |
| Вопрос / выбранный контекст | 64 КиБ / 1 МиБ UTF-8. |
| Функции / описание / схема | До 16 / 4 КиБ / 64 КиБ на функцию. |
| Вызовы | До 8 одновременно, до 256 ID за запрос. |
| Аргументы / текст результата одного вызова | 1 МиБ / 4 МиБ; scoped Core apply принимает до 256 КиБ аргументов. |
| Изображения | До 4; один PNG до 2 МиБ и 4 Мп; суммарно до 4 МиБ PNG. Полное кодирование с base64 помещается в предел stdio. |
| Текст ответа | До 1 МиБ, событие не более 8 КиБ без повреждения UTF-8. |
| Stdio | Одно сообщение до 8 МиБ; чтение по 16 КиБ с обратным давлением. |
| Ожидание RPC / запись pipe | 10 секунд / 5 секунд. |
| Общий ход | До 300 секунд; затем закрытие собственного процесса. |
| Прерывание | До 5 секунд на terminal event, затем завершение процесса; SIGKILL только после 2 секунд неуспешного SIGTERM. |

`turn/interrupt` подтверждает приём команды, но не завершение. `cancel` возвращает ACK только после terminal event или подтверждённого выхода процесса **и** завершения всех уже принятых обработчиков Notebook. Принятая запись не отменяется таймером, и её ACK нельзя выдумать. Обработчик записи должен иметь собственное конечное завершение; пока он удерживает принятую транзакцию, отмена честно остаётся ожидающей. [Протокол ходов и прерывания](https://learn.chatgpt.com/docs/app-server).

Обратные вызовы `onEvent` и `callTool` не должны ждать `cancel` того же запроса: отмена намеренно ждёт освобождения этих обработчиков. Если приложение обнаружило ошибку сохранения события, оно возвращается из обработчика и отдельно запрашивает отмену. Текстовый результат не является квитанцией изменения или подтверждением показа на iPad. Они проверяются прежними владельцами Notebook.

## Воспроизводимая проверка

Из корня проекта:

```sh
Tests/NotebookAgentExecutorHarness/run.sh
```

Этот маршрут компилирует настоящие Swift-файлы исполнителя с изолированным `JSONValue`, запускает настоящий App Server и локальный HTTP-провайдер. Флаг `NOTEBOOK_AGENT_CONTRACT_TEST` существует только в этой отдельной сборке: он допускает проверочный `127.0.0.1` и отключает требование входа без изменения остальных ограничений. Оба application target не определяют этот флаг и не имеют такого конструктора. Проверка не открывает приложение целиком, не использует рабочие тетради и не читает пользовательскую авторизацию.

Восемь сценариев проверяют полный фактический каталог каждого запроса, устойчивый `callId`, передачу ответа и настоящего `input_image` с побайтовым сравнением PNG, предел UTF-8, отмену после реально начатого запроса модели, порядок отмены во время принятого вызова, предел ответа, отказ изменённого профиля/бинарника без единого запроса провайдеру и отдельный отрицательный code-mode контроль. Отчёт — `.build/agent-executor-contract/report.json`. `NotebookAgentExecutorTests` в Mac target отдельно проверяет ранний отказ некорректного разрешения, предел контекста, неизвестный исполняемый файл, безопасность каталога разбиение текста, проверку PNG и последовательность mocked сообщений входа.

Второй маршрут связывает настоящую SQL-базу, прежнюю очередь записи, координатор и тот же настоящий App Server:

```sh
# После сборки настоящего NotebookCore; путь должен содержать согласованные module и object.
NOTEBOOK_CORE_PRODUCTS="$PWD/.build/out/Products/Debug" Tests/NotebookAgentExecutorHarness/coordinator-run.sh
```

Шесть сценариев проверяют замороженные source и PNG после изменения живой страницы, сохранение ответа, один grant-scoped ход с квитанцией, отказ «готово» без изменения, освобождённую очередь во время `input_active`, остановку во время модели и остановку ожидающего ввода инструмента. Каждый завершённый сценарий дополнительно проверяет, что повторные уведомления и выход не меняют SQL-ревизию. Отчёт — `.build/agent-coordinator-contract/report.json`. Изолированный host открывает только созданный этим тестом временный архив; production не получает прямого пути ко второму писателю. `NotebookAgentCoordinatorTests` дополнительно проверяет crash recovery с сохранённой квитанцией, пустую очередь, отказ выхода при заблокированной нативной записи и владельца несохранённых текстовых байтов.

Это доказательство транспортного, инструментального и SQL-контракта, не утверждение о доступности модели конкретной подписке. Реальный управляемый вход, выполнение вопроса из iPad и запись ответа в карточку требуют отдельного сквозного прохода приложения с явным действием входа человека. Подмена отказа аккаунта успешным тестовым ответом недопустима.
